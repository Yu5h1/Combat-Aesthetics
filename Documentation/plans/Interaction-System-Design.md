## 系統階層與關係

```text
CombatAesthetic Unity package
├─ Runtime：既有 2D 戰鬥套件能力（本文不使用）
└─ Samples~/WhiteRoom
   ├─ Runtime：共用角色與意圖（現況）
   │  ├─ CombatActionIntent：玩家、AI、網路共用的一格意圖
   │  └─ CombatEntity：移動、跳躍、碰撞體、速度限制、重設
   ├─ 共同底層：意圖 → 接觸與時間窗 → 判定元件決定正式結果 → 表現（計畫）
   │  ├─ 用法一：雙人互動 ── 兩人同意後開始、一次結束
   │  │  ├─ 互動定義：每個互動一份，描述與其他互動的差異（計畫；格式未決，尚未決定第 6 項）
   │  │  └─ 握手（現況，Handshake/*，第 3 批進行中）→ 碰拳、擊掌、猜拳、擁抱……
   │  └─ 用法二：戰鬥交手 ── 單方面發起、可多人同時進行、有持續狀態（暫停，第二個交付）
   └─ 共用：HUD 事件紀錄、快速重設、第三人稱鏡頭（現況）

依賴方向：
  操作來源（玩家 ICombatInputSource／AI／網路）──意圖──▶ CombatEntity ──每格意圖──▶ 參與者
  接觸元件 ──接觸事件──▶ 判定元件 ──正式結果──▶ 參與者狀態、事件紀錄、表現
```

## 摘要

握手的第一個交付已經做出發起、回應、碰到、握緊時間窗、惡作劇與同時收手（第 3 批會加上握住、比力氣、抓住與掙脫）。計畫要求之後的碰拳、擊掌、擁抱、牽手與背抱共用這套機制，各互動只提供差異：哪些部位接觸、各階段的動作、IK 對準哪裡、套用哪些規則。

本文分出共同底層與互動定義，以計畫排序的前 8 個互動檢查定義表達得出什麼、還缺什麼，說明戰鬥交手怎麼建在同一個底層上，並對照現有握手程式分出可共用與握手專屬的部分。定義的格式不代答，只列出兩種格式各自的影響。

## 問題與目標

### 要解決的問題

1. **握手程式寫死握手**（現況）：狀態列舉 `HandshakeState`、判定元件 `HandshakeArbitrator` 與表現 `HandshakeVisualFeedback` 都寫死右手、兩人、握緊與搖一下，以及大笑、生氣、拍手大笑三種反應。照抄成碰拳或擁抱會複製整套狀態與判定。
2. **新增互動要能不靠 agent**（計畫，「手工編輯（DX）」第 3 項）：每個互動以一份定義描述，新增變化型只要複製定義再修改，不必寫程式。
3. **戰鬥要用同一個底層**（計畫）：攻擊、防禦、擒拿、接拳和雙人互動共用「只送意圖 → 接觸與時間窗 → 判定元件決定正式結果 → 表現」，但戰鬥不是雙人互動的一種。

### 設計目標

1. **判定與表現分開**（計畫）：正式結果只由判定元件決定，聯網時由主機判定並同步；動畫與人形 IK 只影響畫面，各端在本機計算。玩家與 AI 走同一套規則。
2. **動作的區間決定能不能接受操作**（計畫，「動作合理性約束操控」）：每個動作分成可取消、不可控制、可接續等區間，區間內能做什麼由動作本身決定，玩家從角色的動作看得出原因。
3. **差異放在定義裡**（計畫）：接觸部位、各階段的片段、IK 對準位置與套用的規則由定義提供。
4. **時間取自片段**（計畫）：例如惡作劇的判定時間就是「握緊」片段的長度，不另訂數值；計畫明訂可調的數值（握住的放開容許時間、比力氣門檻、抓住時的速度等）放在設定裡。

### 不在本文範圍

- 不改程式，不動第 3 批正在修改的握手檔案。
- 不決定互動定義的格式（尚未決定第 6 項）。
- 不設計網路同步；網路方案由 [網路方案評估](WhiteRoom-Network-Evaluation.md) 負責。

## 共同底層

```text
操作來源（玩家／AI／網路）
   │ CombatActionIntent：MoveInput、Jump、InteractHold／InteractDown／InteractUp、Timestamp……
   ▼
參與者 ── 依目前動作的區間決定接不接受這個意圖 ──▶ 切換動作（伸手、等待、收手……）
   │
接觸元件 ── 「誰的哪個部位碰到誰的哪個部位」──▶ 判定元件
                                                 │ 時間窗取自片段長度
                                                 ▼
                                           正式結果 ──▶ 參與者狀態、HUD 事件紀錄
                                                 │
                                                 ▼
                                           表現：Animator 片段、人形 IK、顏色
```

### 1. 意圖

- **現況**：`CombatActionIntent` 有 `MoveInput`、`Jump`、`CrouchHold`、`CrouchToggle`、`Attack`、`GuardHold`、`ParryTap`、`InteractHold`、`InteractDown`、`InteractUp`、`GlobalReset`、`Timestamp`。玩家（`ICombatInputSource`）與 AI（`HandshakeAiController` 也實作 `ICombatInputSource`）都只產生這個結構，由 `CombatEntity.StepCombat` 每格透過 `OnIntentStepped` 交給握手參與者。雙人互動用到互動鍵三個欄位、移動與跳躍；戰鬥用 `Attack`、`GuardHold`、`ParryTap`。
- **重新按下才發起**（計畫，「發起」列）：互動結束回到站姿時互動鍵還按著，就停在站姿，放開再按下才再次發起。現況由 `HandshakeParticipant` 的 `_requireInteractRelease` 實作：回到站姿時還按著就設旗標，放開後清除；站姿時 `InteractHold` 或 `InteractDown` 且沒有旗標才開始伸手。
- **設計提案**：這條規則所有雙人互動都適用，移到通用參與者，不放在個別互動。
- **聯網時的時間**（計畫，〈連線驗證路線〉）：遠端意圖帶時間，但主機「不把客戶端宣稱的時間直接當成事實」，要在有上限的延遲補償範圍內查核。補償上限與查核方式是〈尚未決定〉第 4 項。

### 2. 動作區間與操作

這是計畫「動作合理性約束操控」對互動系統的要求：能不能開始新的伸手、能不能移動或跳，由當下動作的區間決定，不由程式在動作之外另加開關。

- **現況**：區間的效果已經存在，但寫在程式裡，不在動作上。
  - 伸手（`Reaching`）與等待（`Waiting`）時放開互動鍵就收手，等於整段可取消；碰到發生在伸手或等待都算。
  - 收手（`Withdrawing`）與三種反應時參與者不看互動鍵，計時結束才回到站姿，等於整段不可控制。
  - 移動限制由 `HandshakeParticipant.UpdateEntityLocomotionConstraints` 依狀態列舉設定 `CombatEntity.LocomotionLocked` 與 `SpeedOverride`：握緊、搖一下與三種反應鎖住移動；伸手與等待限制為 `GuardSpeed`；`SpeedOverride` 生效時 `CombatEntity` 不允許起跳。握手參與者也把 `EnableCombatActions` 設為 false。
- **設計提案**：每個階段的動作宣告自己的區間（可取消、不可控制、可接續）與區間內允許的移動方式（原地、慢步、一般走路、可否跳），參與者只問「目前動作的這個區間接不接受這個意圖」。計畫中已確認的移動規則都成為動作的屬性，例如握住時雙方都按著就停在原地、抓住時被抓的一方一般走路速度而抓的一方慢步。互動定義描述這些區間，取代依狀態列舉寫死的移動開關。
- 計畫要求的例子：握緊期間放開的一方，在判定結果與反應結束前仍在收手與反應的不可控制區間，不能開始新的伸手；結束時間可調（第 3 批第 1.4 項）。

### 3. 接觸

- **現況**：`HandContactBridge` 掛在右手的碰撞代理物件上（`RightHandContactCollider`，觸發用 `SphereCollider` 加 kinematic `Rigidbody`），只辨認對方的 `HandContactBridge`。碰到有兩條判定路徑：`OnTriggerEnter`／`OnTriggerStay`，以及 `FixedUpdate` 每個物理格的 `Physics.OverlapSphere`；後者半徑沒有計入縮放。碰撞代理的位置由 `HandshakeVisualFeedback` 在 `LateUpdate` 與 `OnAnimatorIK` 依手腕骨骼擺放，`LateUpdate` 讀到的是套用 IK 之後的位置；目前成立只因碰到之前 IK 權重為 0（見 [驗收紀錄](../WhiteRoom-Acceptance.md)）。
- **計畫**（第 3 批第 1.7、1.8 項）：碰到只保留一條判定路徑，或寫明第二條存在的理由，半徑要計入縮放；碰撞球的位置不能受 IK 影響。掙脫看身體距離，也不受 IK 影響。
- **設計提案**：
  - 接觸元件按身體部位設定（右手、左手、拳頭、手臂、軀幹……），回報「誰的哪個部位碰到誰的哪個部位」，判定元件再核對是否是這個互動要求的部位。
  - 碰撞位置由接觸元件自己依動畫本身的骨骼位置擺放，不放在表現元件裡，讓「IK 不影響接觸」由結構保證，而不是靠 IK 權重剛好為 0。
  - 只有一條判定路徑；採用哪一條等第 3 批第 1.7 項的結論。
  - 有些互動以「條件」取代觸碰：身體距離（掙脫、牽著走的脫手）、雙臂環住身體（擁抱）、沒有接觸（猜拳）。

### 4. 時間窗

- **計畫**：判定時間取自片段長度，例如「碰到後到手掌握緊結束之間」就是握緊片段的長度；惡作劇與同時收手在握緊片段播完時判定。計畫明訂可調的數值另外放設定：握住的放開容許時間（暫定 0.3 秒）、比力氣門檻（預設 1 次）、抓住時的兩個速度、被抓跳起的彈開距離、掙脫門檻（預設雙方手臂完全伸直的距離）、握緊期間放開者的反應結束時間。
- **現況**：`HandshakeArbitrator` 以 `_gripClip.length` 作為握緊時間窗、`_shakeClip.length` 作為搖一下，並把 `_reachClip`、`_withdrawClip` 的長度寫入參與者的 `ReachDuration`、`WithdrawDuration`。三段反應片段存在時以片段長度為反應時間。缺少收手片段時以 0.5 秒代替。

### 5. 判定

- **現況**：`HandshakeArbitrator` 是場景中的單一實例（靜態 `Instance`），一次只處理一組兩人（`_participantA`、`_participantB`）。碰到時兩人都在伸手或等待才開始握緊；握緊期間記錄誰放開；握緊片段播完時判定成功、惡作劇或同時收手。伸手或等待時放開造成的取消由參與者自己處理，只通知判定元件記下 `Cancelled`。
- **計畫**：碰到、成功、惡作劇、同時收手、比力氣的勝負與抓住、掙脫都是正式結果，由主機判定並同步。
- **設計提案**：
  - 雙人互動的判定元件以「一組互動」為單位，同一場景可同時有多組（例如兩對玩家各自握手）；現況的單一實例只能有一組。
  - 參與者只上報意圖與自己的動作區間，正式結果一律由判定元件寫回。取消是否也要成為主機判定的正式結果，計畫沒有規定，見〈尚未決定〉。

### 6. 正式結果

- **現況**：`HandshakeOutcome` 有 `None`、`Cancelled`、`Success`、`Prank`、`BothWithdraw`；惡作劇另由 `LastPranker`、`LastPranked` 帶出放開者與被惡作劇者。結束時發出 `OnHandshakeFinished(HandshakeOutcome)`，判定過程以 `OnArbitrationLog` 發出並寫入 `WhiteRoomHUD.LogAction`。
- **計畫要求的結果與內容**：
  - 成功；惡作劇（放開者、被惡作劇者）；同時收手。
  - 比力氣三種結果：差距超過門檻（勝方與雙方次數）、差距在門檻內且有人按過、0 比 0。
  - 抓住（誰抓住誰）、回到雙方握住、掙脫。
  - 碰拳的碰到與落空。
- **設計提案**：結果以「結果種類＋參與者角色＋數值」描述，例如惡作劇帶出放開者與被惡作劇者、比力氣帶出雙方次數；所有結果走同一個結束事件與事件紀錄。承載的建立與脫離是否算正式結果，要等承載的規則討論後決定。

### 7. 表現

- **現況**：`HandshakeVisualFeedback` 監聽參與者狀態，以 Animator 狀態名稱播放 `Idle`、`Reach`、`Wait`、`Grip`、`Shake`、`Withdraw`、`Laugh`、`Angry`、`ClapLaugh`（後三個不存在就不播）；只在雙方都在握緊或搖一下時開右手 IK，權重 0.85，目標為兩人右手的中點；依狀態把身體顏色漸變為不同色。
- **計畫**：片段到之前，結果只在 HUD 與事件紀錄顯示，雙方用收手回到站姿，不拿其他動作暫代；片段到了只放進設定，不改程式。三段反應片段不必到齊才播（第 3 批第 1.2 項）。
- **現況與計畫的差距**：`41f61db` 的惡作劇要大笑與生氣兩段片段都在才播反應，否則雙方直接收手；這是第 3 批第 1.2 項要修的。
- **設計提案**：Animator 狀態名稱、IK 目標與權重由互動定義提供；表現元件只讀狀態與結果，不擺放碰撞位置。

## 互動定義

計畫（「手工編輯（DX）」第 3 項）要求每份定義描述：接觸部位、各階段的片段、IK 對準的位置、套用的規則（落空、握住、比力氣、抓住與掙脫、承載）。以下結構是**設計提案**：

```text
互動定義
├─ 名稱
├─ 接觸：發起方部位、回應方部位，或改用條件（身體距離、環住身體、沒有接觸）
├─ 階段：每個階段雙方各自的片段，與片段的區間（可取消、不可控制、可接續）
│        和區間內允許的移動
├─ IK：每個階段要對準的部位（一隻手、雙手）與目標（兩手中點、對方某個骨骼加偏移、對方身上的掛點）
└─ 規則與參數
   ├─ 落空：接觸到主要動作結束之間抽手的判定，與單方、雙方放開時的反應
   ├─ 握住：按多久就持續多久、放開容許時間、持續時能否移動
   ├─ 比力氣：只算按下次數、門檻、三種結果
   ├─ 抓住與掙脫：抓住的進入條件、雙方移動速度、跳起彈開距離、掙脫距離門檻
   └─ 承載：一方附著另一方，由下方的人移動（細節待討論）
```

### 階段

**設計提案**：以握手的現況狀態歸納出通用階段，各互動可省略不用的階段。

| 通用階段 | 握手的對應（現況） | 區間（現況程式的效果） |
|---|---|---|
| 伸手 | `Reaching`，片段 `handshake-reach` | 可取消：放開就收手 |
| 等待 | `Waiting`，片段 `handshake-wait` | 可取消：放開就收手 |
| 主要動作 | `Grip`，握緊片段長度就是判定時間窗 | 放開的一方先收手，結果在片段播完時判定 |
| 持續 | 第 3 批的握住、比力氣、抓住（尚無現況） | 計畫：還有一方按著就持續 |
| 結果表現 | `Shaking`、`Laugh`、`Angry`、`ClapLaugh` | 不可控制 |
| 收手 | `Withdrawing`，片段 `handshake-withdraw` | 不可控制，結束回到站姿 |

### 規則之間的關係

規則可以串接：握手是「落空 → 握住 → 比力氣／抓住與掙脫」；擊掌是「落空 → 擊中後短暫的抓住時間窗 → 抓住與掙脫」；碰拳是「落空」，之後可能加上「碰到前抓拳頭 → 拉扯」。所以**設計提案**是規則宣告自己的進入條件（例如抓住可以從「握住中一方放開超過容許時間」或「擊中後的時間窗內」進入），而不是固定只能接在握住之後。

## 前 8 個互動的檢查

依計畫〈後續發展邊界〉「共用的雙人互動系統」的建議順序，逐一檢查上面的定義。「表達得出」指只靠定義與既有規則；「要新增」指定義或底層還缺的能力；「待討論」是計畫已列為未定的細節，本文不代答。

| 順序 | 互動與帶進的新能力（計畫） | 定義表達得出的部分 | 要新增的能力 | 待討論（計畫） |
|:---:|---|---|---|---|
| 1 | **碰拳**：接觸部位改成拳頭、沒有握住 | 接觸設為拳頭對拳頭；規則只開落空；結果為碰到或落空。由 AI 邀請、使用者回應，發起方與回應方本來就不限玩家或 AI | 接觸元件要支援拳頭部位與對應的碰撞位置 | 碰到前換姿勢抓對方拳頭並進入拉扯、拳頭比張開的手難抓多少、拉扯的動作與結果；落空尷尬的表演細節先不展開 |
| 2 | **擊掌**：擊中後的短暫抓住時間窗 | 接觸設為掌心對掌心；規則開落空與抓住與掙脫 | 抓住要能從「擊中後的時間窗內」進入，不只從握住進入（見〈規則之間的關係〉） | 時間窗長度、拉扯的動作與結果 |
| 3 | **猜拳**：沒有接觸，判定雙方同時出手 | 接觸設為沒有接觸 | 新規則「同時出手」：比對雙方出的手勢、以時間窗判定慢出。意圖要能帶出「出哪一種手勢」，`CombatActionIntent` 現況沒有這種欄位；發起條件（距離、面向）也要定義 | 計畫只列「同時出手，以時間窗判定慢出」，操作方式與勝負表現未定 |
| 4 | **擁抱**：多部位接觸，兩人身體貼近 | 規則開落空（時間窗內閃開）、握住（按多久抱多久）、抓住與掙脫 | 接觸改為條件「雙臂環住身體」，由多個部位共同成立；兩人身體要能貼近，現況握手參與者把身體碰撞半徑設為 0.25；IK 要同時對準雙手、目標在對方背後 | 計畫已確認這些差異，表演細節未定 |
| 5 | **牽手與牽著走**：連著的時候一起移動 | 接觸為手對手；規則開握住、抓住與掙脫；手以人形 IK 黏在對方手上 | 握住期間能否移動要由定義決定（握手是雙方都按著就停在原地，牽手是雙方慢步移動）；脫手以身體距離判斷 | 用哪隻手、並排或一前一後、誰帶著走、牽著能不能跑跳 |
| 6 | **拉人起身、攙扶**：雙方狀態不對等 | 接觸為手對手或手臂搭肩 | 發起前要檢查對方的狀態（倒地、受傷），結果要改變對方的持續狀態（起身、攙扶時移動變慢）；這兩者跨到戰鬥的持續狀態，現況 `CombatEntity` 沒有倒地或受傷可供檢查。倒地的一方怎麼回應也要定義 | 計畫列入「其他雙人互動」，細節都待討論；和戰鬥中救起失去戰力的隊友相關 |
| 7 | **背與其他承載**：一方附著另一方，由下方的人移動 | 規則開承載 | 承載規則本身：附著的掛點、上方的人的移動輸入如何處理、下方的人移動時兩人一起移動 | 承載的動作、上下的方式、能否掙脫 |
| 8 | **接住跌倒的人**：回應的是對方的一個意外 | 規則可沿用時間窗與落空（沒接住） | 發起不來自對方的意圖，而來自一個事件（對方往後倒）；現況沒有跌倒狀態可觸發 | 計畫只列「在時間窗內接住」，細節待討論 |

**結論**：碰拳、擁抱只需擴充接觸元件；擊掌與牽手要求規則的進入條件與持續時能否移動由定義決定；猜拳、拉人起身、接住跌倒的人要新增底層能力（手勢意圖、狀態前置條件與持續狀態、由事件發起）；承載的規則本身尚未定義。這與計畫「優先做能讓通用互動系統多一種能力的」一致：每個互動都會帶進一項定義表達不了、要先補上的能力，「新增變化型不必寫程式」只對已具備的能力成立。

## 戰鬥交手如何建在同一個底層上

計畫（使用者 2026-10-31）：戰鬥與雙人互動共用底層，但戰鬥不是雙人互動的一種。共同底層是「只送意圖 → 碰撞體接觸與時間窗 → 判定元件決定正式結果 → 表現」，判定與表現分開，玩家與 AI 走同一套規則。上面有兩種用法：

| | 雙人互動 | 戰鬥交手 |
|---|---|---|
| 開始 | 兩人同意後開始 | 單方面發起，攻擊不必等對方同意 |
| 人數 | 一組兩人 | 可多人同時進行；一個人可能同時被多人攻擊（首輪最多 2 名玩家與 2 名 AI） |
| 狀態 | 一次結束，結束就清空 | 生命、受力、硬直與失去戰力會持續 |

### 共用與分開

- **共用**（計畫）：意圖結構、角色移動與動作區間、接觸元件、時間取自片段、判定元件產生正式結果、表現只讀結果、事件紀錄與快速重設。計畫〈最小行為設計提案〉對戰鬥也要求「依姿態、動作區間與能力接受或拒絕意圖」，與雙人互動的「動作合理性約束操控」是同一條原則。
- **設計提案**：
  - 戰鬥的判定元件要同時處理多筆交手，每筆以「攻擊者、目標、攻擊實例」辨識，避免同一次接觸重複計傷（計畫〈最小行為設計提案〉「攻擊與接觸」）；雙人互動的判定元件以一組兩人為單位。兩者共用接觸與時間窗的處理方式，各自持有不同的判定規則。
  - 持續狀態（生命、受力、硬直、失去戰力）屬於角色，不屬於任何一次交手或互動；交手的結果寫入角色的持續狀態，互動結束時清空的只有互動自己的狀態。拉人起身、攙扶要讀寫的也是這份持續狀態。
  - 互動定義是雙人互動用的；戰鬥招式是否用同一種定義格式，見〈尚未決定〉。

### 對應關係（計畫）

| 戰鬥 | 對應的底層概念 | 本文不代答的部分 |
|---|---|---|
| 攻擊 | 不需回應的發起，依動畫的有效區間開關攻擊接觸 | 招式與數值 |
| 普通防禦 | 時間窗內的回應：右鍵警戒，自動嘗試防禦面向範圍內的攻擊，背後不自動擋 | — |
| 精準防禦 | 更短時間窗內的回應：計畫〈最小行為設計提案〉建議在來襲時機快速按下放開右鍵，成功時中止對方原本連續進攻 | 確切時間窗與動畫來源（實作前收斂） |
| 擒拿 | 抓住與掙脫 | 是否消耗體力、與比力氣的數值關係 |
| 接拳 | 接觸加抓住：雙手張開舉在肩膀正前方，用掌心接對方的拳 | 接住後是否進入拉扯、與普通／精準防禦的關係（戰鬥驗證恢復時討論） |

摔投、扛起後丟出、從背後架住雙臂、雙手推開、被抓住時反抓回去屬第二個交付，計畫規定等戰鬥驗證恢復時再談。

### 整理成通用系統的順序（設計提案）

計畫規定在握手三批完成、開始第二個互動時整理。建議順序：

1. 握手第 3 批驗收後，以當時的程式重做本表（第 3 批會新增握住、比力氣、抓住與掙脫，也會改動接觸與 IK）。
2. 先抽出共用部分：參與者的發起與區間、接觸元件、判定元件的計時與結果事件、表現的播放與 IK；握手改由一份定義描述，用握手的回歸測試確認行為不變。
3. 再做碰拳，驗證接觸部位可以設定。

### 驗收方向（設計提案）

1. 握手改由定義描述後，三批的判定、表現與回歸測試結果不變。
2. 碰拳的碰到與落空只靠定義與已補上的拳頭部位完成，不另寫判定程式。
3. 戰鬥場景 `Combat/WhiteRoom.unity` 的移動、跳躍、攻防與鏡頭不受影響。

## 互動定義的格式（尚未決定第 6 項）

計畫原文：

> 互動定義的格式：存成 Unity 的設定資產（Inspector 編輯最方便，只有 Unity 能用），或跨平台資料檔（沿 data-driven 方向，Web 工具也能編輯、其他平台可讀，但 Unity 內要另做編輯介面或改用 Web 工具）。計畫方向是跨平台累積，agent 傾向跨平台資料檔；做通用互動系統前決定。

本文不代答，只列出兩種格式各自對設計的影響。

| 影響的地方 | Unity 設定資產 | 跨平台資料檔 |
|---|---|---|
| 片段的參照 | 直接參照 `AnimationClip`，時間取自片段長度不必另外解析 | 以名稱或路徑參照片段，Unity 端要把參照解析成片段；名稱不一致時要能報錯 |
| 部位與 IK 目標 | 可直接用 Unity 的列舉（如 `HumanBodyBones`、`AvatarIKGoal`） | 以文字描述，各平台各自對應到自己的骨骼 |
| 手工編輯（DX 第 3 項：複製定義再修改） | 在 Project 視窗複製資產，用 Inspector 修改；Play 中修改能保留 | 複製檔案再修改；Unity 內要另做編輯介面，或改用 Web 工具 |
| 片段更新（DX 第 4 項） | 動畫編輯器輸出後要匯入成 Unity 片段，再在資產上指定 | 定義以名稱參照片段，片段更新後定義不必改；仍要先完成匯入 |
| 其他平台 | 只有 Unity 能讀 | Web 工具與其他平台能讀，符合計畫的跨平台累積方向；data-driven 本身的資料格式仍待釐清（〈尚未決定〉第 1 項） |
| 版本比對 | Unity 的 YAML，可讀但有 Unity 專屬欄位 | 純文字資料，容易比對與驗證 |
| 聯網 | 兩種都不上網路：計畫規定片段與 IK 各端自己計算，只傳意圖與正式結果；兩端要有相同的定義 | 同左 |

兩種格式都相容的一點（**設計提案**）：判定與表現只讀一份記憶體中的定義資料，不直接依賴儲存格式；這樣決定格式前就能先整理共同底層。

## 尚未決定

1. **互動定義的格式**（計畫〈尚未決定〉第 6 項）：Unity 設定資產或跨平台資料檔，做通用互動系統前決定；兩者的影響見上一節。
2. **戰鬥招式是否也用互動定義的格式描述**（本文提出）：計畫只規定雙人互動用定義；戰鬥用同一種格式可共用編輯方式，但戰鬥有多人與持續狀態，欄位會不同。
3. **取消是否算正式結果**（本文提出）：計畫列出的正式結果不含取消；現況由參與者自己處理取消。聯網時若取消也要由主機判定，伸手與等待中的放開也要走判定元件。
4. **通用層的位置**（本文提出）：留在 Sample 內，或移到套件 Runtime；計畫〈尚未決定〉第 3 項規定本輪不改既有 Runtime。
5. **怎麼選擇目前的互動**（本文提出）：計畫已確認「玩家選『握手』作為目前的互動動作」，有多個互動後怎麼選（HUD、快捷鍵或依情境）尚未討論。
6. 各互動計畫已列為待討論的細節見〈前 8 個互動的檢查〉的「待討論」欄；擒拿與比力氣的數值關係等戰鬥驗證恢復時再談。
